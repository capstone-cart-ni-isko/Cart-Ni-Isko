1.1 FRONTEND — one React SPA with two separate portals  [NOW-C]
--------------------------------------------------------------------------------
  Stack/entry: Vite + React (JSX), React Router, single app in /frontend.
  main.jsx: applies saved theme (isko_theme) before paint, prefetches
  /products/filter {status:active}, registers the PWA service worker (prod
  only), wraps App in an API error boundary.
  Provider tree (App.jsx): Toast > Theme > Auth > Admin > Cart > Wishlist, then
  ScrollToTop + GlobalApiLoader around <Routes>.
  Portals are strictly separate [RULE-A R03]: customer screens and /admin/*
  screens use different contexts (AuthContext vs AdminContext) and different
  in-memory session slots (services/session.js, tagged kind). Sessions are NOT
  persisted -> a page refresh signs the user out [SRS-B REQ-ALR-01].
  Guards:
    RequireAuth    -> no currentUser: <LoginPromptModal> (mobile routes straight
                      to /signin); used by every private customer screen.
    RequireAdmin   -> no currentAdminUser: <Navigate to="/admin/login">.
    RequireRole    -> roleKey not in roles: soft bounce to /admin/dashboard.

1.2 BACKEND — Laravel 12 JSON API + Sanctum  [NOW-C]
--------------------------------------------------------------------------------
  Stack: PHP ^8.2, Laravel 12, Laravel Sanctum bearer tokens. Responses are
  JSON {success, message, data}. Unauthenticated -> 401 JSON (never a redirect).
  Middleware chain: api -> auth:sanctum (except public routes) -> role:* ->
  CacheReads (GET only).
    EnsureRole ranks: role:staff = ANY employee (rank 3), role:admin = ADMIN or
    SUPER ADMIN (rank 2), role:super_admin = SUPER ADMIN (rank 1). A customer
    token on any employee endpoint -> 403 "Employee authentication is required."
  Controllers: AuthAPI, CartAPI, CheckoutAPI, OrdersAPI, PosAPI, AppointAPI,
  TrackingAPI, ProductsAPI, AccountsAPI, ReviewsAPI, SettingsAPI, ShiftAPI,
  NotifAPI, AccessAPI, ReportsAPI, WishlistAPI, UploadAPI, HealthAPI, plus base
  Controller helpers (settingValue -> Setting::getValue, notifyEmployee,
  notifyCustomer, orderQr signing).

  COMPLETE ROUTE MAP (routes/api.php)
  Public (no token):

         | /auth/recover_credentials

    POST /orders/add   PUT /orders/update   DELETE /orders/remove

  appointment/account queries use self vs master scope (master = any employee
  token can read all customers' appointments/account list).

  CROSS-CUTTING
  Scheduler (routes/console.php):
    - NotificationFollowUpJob every 15 min (env ENABLE_NOTIFICATION_FOLLOWUPS,
      default true) for unread customer notifications >= 24h (comments say 2h).
    - Minute heartbeat (feeds /health/scheduler: RUNNING, or STALLED -> 503
      when older than 120 min).
    - AcademicPeriodRoster hourly: preset roster generator (rule R08). It runs
      only when Setting academic_period_start <= today (code default
      "2027-08-02") and once per term (marker file). The settings table is
      EMPTY, so today the job reports "the term has not opened yet" and never
      generates the roster [DELTA D22].
  Uploads: POST /uploads (auth) writes base64 images under public/uploads/img/,
  returns a public URL. No S3.
  Mail/queue: MAIL_MAILER=log (no SMTP credentials), queue=sync -> no real e-mail
  is ever delivered [DELTA D03/D21].
  Tests: PHPUnit 8 Feature + 1 Unit on sqlite :memory: (phpunit.xml forces
  sqlite). Verified this session: `php artisan test --filter checkout` -> 3
  passed (the suite stays green even though live checkout is broken, see D20).
  Security: BCrypt passwords, Sanctum tokens, role middleware, PayMongo webhook
  HMAC verification, HMAC-signed order QRs (CNI-ORDER-{id}.{sig}), and REVOKEs
  on public schema roles (see 1.3). Laravel bootstraps error_reporting(-1) and
  converts PHP warnings into ErrorException (relevant to D23).

2. EMPLOYEE ROLE-BASED ACCESS MANAGEMENT
================================================================================
  Rule baseline [RULE-A EMPLOYEE + SRS-B]:
    - Exactly one category per employee: "super admin" | "admin" | "staff"
      (R07); the store must have >= 1 super admin and >= 1 employee overall;
      employees must currently be BU students; login is own BU e-mail + password
      (BU e-mail unique to one employee); ONLY super admin may create employee
      accounts.
    - Access matrix (view / edit):
      staff       VIEW  employee schedule, active+inactive appointments,
                        inventory, product details, past walk-in orders,
                        active+inactive pre-orders, personal notifications
                  EDIT  personal profile details, personal settings
      admin       VIEW  employee schedule, system notifications, personal
                        notifications
                  EDIT  active/inactive appointments, inventory, add/modify
                        product details, add/modify/complete walk-in orders,
                        active/inactive pre-orders, personal profile/settings
      super admin VIEW  personal notifications
                  EDIT  customer accounts, enroll/manage employee accounts,
                        employee schedules, appointments, inventory, product
                        details, walk-in orders, pre-orders, system settings,
                        system notifications, personal profile/settings.
    - UI rule [RULE-A REQ-EMP_HOME-01]: staff must never see Dashboard, Walk-in
      Orders, Reviews and Sales entries.

  Enforcement today [NOW-C] (layers, outermost first):
    1) Router: /admin/pos and /admin/settings wrapped in RequireRole(['ADMIN',
       'SUPER ADMIN']); everything else only RequireAdmin.
    2) Sidebar: staff does not see Register (POS) or Settings.
    3) API middleware (section 1.2 role column): staff-only reads (accounts,
       shifts GET, notif create/distribute, tracking update/close, access log,
       products/orders, reports, settings display); admin-level mutations (POS,
       products write, reviews moderate, settings update, shifts write,
       appoint/close); super-admin-only (emp_signup, accounts type/delete/
       disable/recover).
    4) Controller checks: order status changes require isAdmin (staff STAFF
       tokens get 403 "Administrator access is required."), appointments use
       self vs master scope, account updates are self-scoped/allow-listed,
       reviews require ownership/purchase.
    5) Customer tokens are always rejected on employee endpoints (403
       "Employee authentication is required.").
  Result vs matrix [DELTA]: route-level roles are coarser than (A)'s matrix —
  e.g. OrdersAPI is "any token" but internally admin-gated (compliant), while
  ReportsAPI/AccountsAPI reads are open to all staff (staff is supposed to have
  no customer-account management). Deltas: D05 (staff still sees Dashboard/
  Reviews/Analytics), D07 (staff/master scope reads across customers), D24

C5. ONLINE PAYMENTS  [RULE-A R09 "pre-orders are paid online only"]

  dispatch_type, appoint_id|address, ...} inside one DB transaction:
    1 already-completed orders return idempotently (200)
    2 re-price items from product rows, verify stock, compute fee/total, verify
      pay_given >= total due
    3 create the payment row (PAY-<16>) + pickup or delivery+parcel rows

      qty <= low_stock_threshold (default 5) [SRS-B REQ-IM-03: priority

  verifies the HMAC signature, and on "succeeded" marks the order PAID, writes
  the payment row and notifies. The browser then re-calls /checkout/payment to
  commit (fallback "success on failure" in the UI).
  [NOW-C — CRITICAL]: on the LIVE database this commit returns HTTP 500
  "Failed to integrate payment" and rolls everything back, because
  CheckoutAPI::settingValue() queries columns setting_key/setting_value that do
  not exist (live settings has key/value). Verified this session with a
  read-only SELECT on live (SQLSTATE 42703) and reproduced why tests stay green
  (SQLite treats the unknown quoted identifiers as string literals -> NULL ->
  default 5). POS is unaffected (it uses Controller::settingValue ->
  Setting::getValue). [DELTA D20]
  Also [DELTA D04]: PayMongo keys are empty in .env (gateway unusable), the
  webhook route sits inside auth:sanctum (an external PayMongo callback would be
  401), and PayMongoService::refundPayment is never called.

6. ORDER STATE MACHINE
================================================================================
  Statuses: TO PROCESS, TO CLAIM, TO RECEIVE, CANCEL REQUESTED, RETURN
  REQUESTED, CLAIMED, UNCLAIMED, CANCELLED, RETURNED, REFUNDED, PAID.
  System-set: checkout pickup -> TO CLAIM; checkout delivery -> TO RECEIVE;
  webhook success -> PAID; completing statuses (CLAIMED/CANCELLED/RETURNED/
  REFUNDED) stamp ord_completed.

  Allowed staff/admin transitions (OrdersAPI, admin token required):
    TO PROCESS       -> TO CLAIM, TO RECEIVE, CANCEL REQUESTED,
                        RETURN REQUESTED, CANCELLED
    TO CLAIM         -> CLAIMED, UNCLAIMED, CANCEL REQUESTED,
                        RETURN REQUESTED, CANCELLED
    TO RECEIVE       -> CLAIMED, UNCLAIMED, CANCEL REQUESTED,
                        RETURN REQUESTED, CANCELLED
    CANCEL REQUESTED -> CANCELLED
    RETURN REQUESTED -> RETURNED
    CLAIMED          -> RETURN REQUESTED, RETURNED, REFUNDED
    RETURNED         -> REFUNDED, CLAIMED
    Anything else -> 409 "Invalid order status transition."
  QR transitions (POST /tracking/scan): TO CLAIM --employee--> TO RECEIVE;
  TO RECEIVE --customer--> CLAIMED (and delivery -> DELIVERED); wrong actor or
  wrong state -> 409.
  Customer self-service (PUT /orders/update, own order only):
    - CANCEL REQUESTED or RETURN REQUESTED from TO PROCESS|TO CLAIM|TO RECEIVE
    - RETURN REQUESTED from CLAIMED
    - everything else -> 403 "This order change requires staff review."
    - walk-in phone 0000000000 additionally requires an open VISIT
      appointment, else 403 + custlog entry.
  Note: UNCLAIMED is a staff marking for a pickup that was never claimed (via
  tracking/update or orders/update); REFUNDED is issued by admin/super admin.

9. KNOWN DELTAS AND DEFECTS (honest gaps vs (A)/(B))
================================================================================
  D01 Slot geometry: implemented 30-min CLAIM / 10-min VISIT, capacity 10/1,
      minimum staff 1 (CLAIM) / 2 (VISIT); the governing (A) rule requires
      exactly 10-minute slots, max 5 pickup + 1 visit, >= 1 employee available.
      The implementation matches (B) REQ-AB-01/02/03 exactly, so this delta is
      against (A) alone — the new SRS must resolve the conflict, and by the
      stated precedence (A) wins.
  D02 No server-enforced OTP anywhere: signup /verify-otp / forgot-password
      codes are accepted client-side; REQ-EMP_LOGIN-09/10 (6-digit e-mail OTP)
      not implemented; REQ-EMP_LOGIN-03 (auto re-mask after 3s) not enforced.
  D03 Recover-password endpoint is a stub (always a generic success message);
      no mail is ever sent (MAIL_MAILER=log, no SMTP).
  D04 REFUNDED/CANCELLED/RETURNED move no money and restore no stock;
      PayMongoService::refundPayment is unused; PayMongo keys are empty in
      .env; the webhook route sits inside the sanctum group.
  D05 PRODVAR / PRODSALES of the new schema are not separate tables (product
      JSON columns + per-product counters stand in); bag rows live in orders
      with a CART- prefix instead of a BAG table.
  D06 BUeño/guest categorization, BU e-mail domain and BU e-mail uniqueness are
      not validated at signup; cust_type stores 'Student'/'WALK-IN'.
  D07 Staff visibility rule REQ-EMP_HOME-01 (hide Dashboard/Walk-in/Reviews/
      Sales from staff) only partially applied (only Register and Settings are
      staff-hidden; Walk-in IS hidden by RequireRole, but the "Analytics" =
      Sales screen is not); staff can still open Dashboard/Reviews/Analytics
      and read all customers/accounts/appointments (master scope) beyond the
      view-only matrix.
  D08 Customer addresses are stored per-device (localStorage) and not synced as
      customer rows, though checkout uses the profile address.
  D09 Delivery address book is not persisted server-side; delivery uses the
      profile address or a typed one.
  D10 Notification preferences screen is informational only; the follow-up job
      uses a 24h unread threshold (comments say 2h).
  D11 AdminReports screen is unrouted; some inventory filters, POS buttons
      (Hold/Discount/Recent Sales), delivery Retry/Contact, review Reply/
      Escalate and settings sections are UI stubs.
  D12 Real-time updates are polling/caching only (Reverb installed, unused).
  D13 Walk-in POS update endpoint lacks transition/ownership validation.
  D14 ReportBuilder references a non-existent appoint_deleted column and an
      undefined dutyShifts relation (appointments/staffing reports fragile).
  D15 Employee top ribbon lacks the required home/QR/dark-mode/settings icons
      (FLOW-EMP_HOME-04/07/09-13); the portal has no theme toggle; the scanner
      exists only inside the Pickup screen.
  D16 Customer menu drawer omits the required "settings" entry
      (FLOW-CUST_HOME-03); Settings is still reachable from Profile/account.
  D17 Booking/rescheduling an appointment sends no notification, and
      notification rows carry no link column (only closed/unavailable slot
      notices deep-link); REQ-OT-01's silent set is wider in code.
  D18 No employee notification inbox exists (empnotif rows are never rendered
      or read; the bell shows a client-side alert feed) and the cust_unread /
      emp_unread counters required by (A) do not exist in the live schema and
      are never maintained.
  D19 The required left-rail "Logout" entry (icon+label) is missing entirely
      (FLOW-EMP_HOME-05) and the logout confirmation popup required by
      FLOW-EMP_HOME-22 does not exist either — the top-bar "Sign out" logs the
      employee out immediately without asking.
  D20 CRITICAL — live online checkout is broken: CheckoutAPI::settingValue()
      selects setting_key/setting_value from settings, but the live table has
      key/value columns (SQLSTATE 42703 confirmed by a read-only live query).
      POST /api/checkout/payment therefore throws inside the transaction and
      returns HTTP 500 "Failed to integrate payment" with a full rollback, so
      no pre-order can be committed online today. Feature tests stay green
      because SQLite treats the unknown double-quoted identifiers as string
      literals (WHERE never matches -> NULL -> default threshold 5). POS
      checkout is unaffected (Controller::settingValue uses Setting::getValue).
  D21 Customer account recovery cannot complete: /auth/recover_credentials is a
      stub, the OTP step is client-side, and the reset step posts
      {identifier,password} to PUT /auth/update_credentials, which is inside
      auth:sanctum (401 for a signed-out user) and requires
      current_password + new_password (422) — verified against routes,
      validator and ForgotPassword.jsx.
  D22 Scheduling rules dormant: the preset-roster job never runs (empty
      settings, code default academic_period_start 2027-08-02 -> "term has not
      opened yet") and the >=180 minutes/week rule has no implementation.
  D23 Delivery tracking read fails: TrackingAPI::createFulfillmentTrack uses an
      undefined $delivery variable in the delivery branch; Laravel converts the
      warning into an ErrorException that the method's catch turns into HTTP 500
      "Failed to retrieve fulfillment track" (pickup track unaffected).
  D24 Minor UI inconsistencies: the command palette's "?search=" is never read
      by any admin screen; the bell dot is drawn even at 0 alerts; the
      Storefront screen is openable by staff although saving is admin-only
      (PUT /settings/update -> 403 for them); the customer menu drawer's Logout
      entry has no confirmation popup/toast (Profile/Settings/account sidebar
      do).
  D25 Account deletion is a reversible soft delete: DELETE /accounts/delete
      only sets cust_deleted/emp_deleted and revokes tokens, while (B)
      REQ-UM-03 requires a confirmation-gated, irreversible purge of all
      associated data. Action logs exist (emplog) but no reason field is
      captured [REQ-UM-04].
